RegReport — Documentation

Multi-entity regulatory reporting dashboard: tracking, analysis and comparison of regulatory KPIs (CET1, LCR, NSFR, Leverage Ratio), deadlines, daily reports and projects.

React 18 + TypeScript Vite Tailwind CSS Recharts .NET 8 + EF Core SQL Server Windows Auth 100% offline

★What's new — v3.2 (September 2026)

Reporting & Workbench

  • Richer Management Report: Leverage and Large Exposures tabs; the Overview gains a second row of tiles (top non-sovereign exposure, total assets, total equity, YTD P&L).
  • K-LER import (FINMA): the Large Exposure template feeds the register — counterparty type, sovereign family shown as exempted (excluded from the breach counter), Direct / Indirect / CRM breakdown (risk-transfer mitigation), stacked chart of direct-net-of-CRM vs indirect.

  • Flexible CET1 bridge: editable manual lines (acquisitions, disposals, redemptions…), timestamped and signed; the P&L bar follows the YTD flow from the monthly statements.
  • More reliable P&L import: the monthly net = reported IFRS result, self-checked against the file's control line, YTD columns.

Production / MERCURY

  • Full Adjustments module: matching by load collection, intercompany (HYPERIOD_INTERCO → CounterpartyBookingCenterId), balance-sheet impact preview with eliminations per consolidation scope, one-shot .sql / Excel generation, manual line, mappings persisted in the database, audit trail.

New modules

  • Projects (port of the "Pilote" tool): Kanban with customizable columns and drag & drop, filterable List view, Gantt timeline (day/week/month zoom, expandable subtasks), subtasks, comments, activity log signed by the Windows user, per-task file attachments (stored in the database, also visible in the Library).
  • Library: documents stored in the database (re-downloadable, offline), folder tree with subfolders, renaming, drag & drop, built-in viewer (PDF/HTML/markdown), automatic archiving of the source files imported in the Workbench (entity/period/type).
  • Team & Contacts: editable team + directory of contacts outside the team (department, company, key topics, comments) — searching "bank guarantee" surfaces who to call, with a link to the procedure in the Library.

Platform

  • Dark mode (toggle in the header); version + environment badge (vX.Y.Z · PROD/TEST/DEV/LOCAL) fed by GET /api/meta.
  • Built-in schema migrator: on every startup the API applies additive, idempotent schema changes (never a DROP) and records them in __SchemaMigrations — releases deploy without SSMS scripts and without data loss (see docs/UPGRADES.md).
  • Reworked Admin: System panel (version, environment, MERCURY, migrations), data inventory, entity management (cascading rename across all datasets, risk appetite, diagnostics and Library documents, with merge-collision detection), JSON backup & restore, collapsed and labelled CSV feeds.
  • Daily Reports based on the entities actually present in the data (no more hard-coded list), Large Exposures card at K-LER level.
  • Fully offline: self-hosted font, no CDN dependency, vendored npm cache + NuGet kit; one-zip release (scripts\release.ps1, the API serves the front-end).

4The data flow (important)

This is the heart of the application. Everything goes through a single central state.

constants.ts (seed)
      │
      ▼
dataRepository.load() ──► DataContext (state: CentralData) ──► useData() ──► Pages
      ▲                            │
      │                            ▼ (changes via setData)
dataRepository.save() ◄──── automatic persistence (400 ms debounce)
  1. On startup, DataProvider calls dataRepository.load(). The repository picks its source from VITE_API_BASE_URL: empty → local mode (reads localStorage or the seed); set → API mode (GET {base}/data).
  2. The data lives in a single CentralData object exposed through the useData() hook.
  3. Each page reads data and changes it via setData(...).
  4. On every change, an effect persists automatically (400 ms debounce): localStorage.setItem locally, or PUT {base}/data in API mode.
Key pointNo component knows where the data comes from. To switch to the back-end, the only thing that changes is the VITE_API_BASE_URL variable.

The useData() hook

const {
  data,            // CentralData: all the app's data
  setData,         // to change the data
  allEntities,     // string[]: entities present (derived)
  allDates,        // string[]: dates present (derived, sorted desc.)
  getKpisForDate,  // (entity, date, currency?) => CalculatedKpis | null
  isLoading,       // initial load in progress
  loadError,       // load error (API mode)
  mode,            // 'local' | 'api'
} = useData();

  • CalculatedKpis = what calculateKpis() derives:

6.2 Deadlines /deadlines

Sortable list and visual calendar; each deadline has a status (completed / inprogress / upcoming), a change history and attachments. Computes the regulatory due date (+10 business days).

6.3 Admin /datamanagement

  • System: version, environment (PROD/TEST/DEV), MERCURY connection, applied schema migrations.
  • Data inventory: row counters per dataset.
  • Entities: cascading entity rename across all datasets (+ risk appetite, diagnostics, Library documents), controlled merge.
  • Backup & restore: full ZIP archive (data + Library documents, no server rights needed) and JSON snapshot; the real safety net remains BACKUP DATABASE on the SQL side.
  • CSV feeds (collapsed): daily LCR, deadlines, capital KPIs (legacy), counterparty RWA — replace / append modes.
  • Risk Appetite: red/amber thresholds per entity — drives every status color in the reports.

7The design system ("EFG" style)

The visual identity is inspired by a private-banking corporate deck: sober, airy, light-weight headings, a single accent color (deep red) used sparingly.

  • Palette: defined once in src/theme.ts (PALETTE, CHART_COLORS, STATUS_COLORS) and mirrored by name in tailwind.config.js. To change the whole visual identity, edit these two files.
  • Layout components: PageHeader, SectionHeader (title + muted suffix), BulletList (red square bullets), Card, Modal, InfoBox, Select, TabButton.
  • Charts (Recharts): every color comes from CHART_COLORS / PALETTE. Light hairline grids, compact heights, red reserved for emphasis / totals.

8Persistence & reset

  • API mode (nominal): everything lives in SQL Server, 100% relational schema — every value has its own column. Schema changes are applied automatically when the API starts (built-in migrator, __SchemaMigrations table — see docs/UPGRADES.md). Full backup: BACKUP DATABASE RegReport (also covers the Library documents).
  • Local mode (demo): without an API, the data lives in localStorage (key regReportData); "Reset" in Admin returns to the constants.ts seed.

9Conventions & good practices

  • Strict TypeScript: npm run lint must stay green.
  • Lazy loading: each page is a separate chunk. Heavy libraries (jsPDF, html2canvas) are imported dynamically.
  • Colors: never hard-code a hex — use theme.ts (charts) or the brand-* Tailwind tokens (classNames).
  • Data: always go through useData() / setData(), never read localStorage directly from a page.

Connecting a back-end

.NET 8 + Entity Framework Core + SQL Server

How to replace the localStorage storage with a real ASP.NET Core Web API back-end, and plug the existing front-end into it without rewriting the components. The front-end is ready: dataRepository.ts switches to API mode as soon as VITE_API_BASE_URL is set.

ATarget architecture

┌──────────────────┐   HTTPS / JSON   ┌────────────────────────┐      ┌────────────┐
│ React/Vite front │ ───────────────► │  ASP.NET Core Web API  │ ───► │ SQL Server │
│ dataRepository   │ ◄─────────────── │  Controllers + EF Core │ ◄─── │  (MSSQL)   │
└──────────────────┘                  └────────────────────────┘      └────────────┘
     'api' mode                          /api/data, /api/kpis, ...

Two storage strategies, your choice:

  • Option A — "Document" (fast start): a single table storing the full CentralData JSON. Works immediately with GET/PUT /api/data.
  • Option B — Relational (target): a normalized SQL schema (one table per resource) for fine-grained querying, auditing and security.
TipYou can start with A and migrate to B without touching the front-end: the front always talks to /api/data; only the controller's implementation changes.

Option A — /api/data controller (document)

[ApiController]
[Route("api/data")]
public class DataController : ControllerBase
{
    private readonly AppDbContext _db;
    public DataController(AppDbContext db) => _db = db;

    [HttpGet]
    public async Task<IActionResult> Get()
    {
        var doc = await _db.CentralDataDocuments.FindAsync(1);
        return Content(doc?.Payload ?? "{}", "application/json");
    }

    [HttpPut]
    public async Task<IActionResult> Put()
    {
        using var reader = new StreamReader(Request.Body);
        var json = await reader.ReadToEndAsync();
        var doc = await _db.CentralDataDocuments.FindAsync(1)
                  ?? _db.CentralDataDocuments.Add(new() { Id = 1 }).Entity;
        doc.Payload = json;
        doc.UpdatedAtUtc = DateTime.UtcNow;
        await _db.SaveChangesAsync();
        return NoContent();
    }
}

DOption B — Relational schema (target)

Normalized schema mirroring types.ts, 100% relational: nested structures are flattened into columns (CET1 breakdown, key metrics) or stored in child tables (liquidity per currency, history/attachments). No JSON columns, except the importMapping setting (Excel parser config) in Settings.

-- Raw KPIs (one record per entity + date)
CREATE TABLE dbo.KpiHistory (
    Id           INT IDENTITY PRIMARY KEY,
    Entity       NVARCHAR(64)  NOT NULL,
    [Date]       DATE          NOT NULL,
    Cet1Capital  DECIMAL(18,2) NOT NULL,
    CreditRWA    DECIMAL(18,2) NOT NULL,
    MarketRWA    DECIMAL(18,2) NOT NULL,
    OpRWA        DECIMAL(18,2) NOT NULL,
    Tier1        DECIMAL(18,2) NOT NULL,
    Exposure     DECIMAL(18,2) NOT NULL,
    BreakdownEquity … BreakdownDividend DECIMAL(18,2) NULL, -- 7 columns
    CONSTRAINT UQ_KpiHistory UNIQUE (Entity, [Date])
);

-- KpiLiquidity: 1 row per currency (FK KpiHistory, flat columns)
-- DeadlineHistory / DeadlineAttachments: child tables of the deadlines
-- RiskAppetite: 1 row per entity (thresholds as columns)
-- Bilan: single-row table (one column per currency)
-- + Deadlines, CounterpartyRwa, LargeExposures, TeamMembers,
--   Projects, ProjectTasks, Settings (importMapping only)

Map each table to an EF Core entity and expose one DbSet<> per resource. The /api/data controller then becomes an aggregator that recomposes CentralData from the tables (and the reverse on PUT).

FSecurity (recommended in banking)

  • Authentication: Microsoft Entra ID (Azure AD) via OpenID Connect. API: AddAuthentication().AddJwtBearer(...) + [Authorize]. Front: access token (MSAL.js) injected into ApiRepository.headers() (the slot is already prepared).
  • HTTPS mandatory (app.UseHttpsRedirection()).
  • Audit: the UpdatedBy / UpdatedAtUtc columns trace every write.
  • Validation of the payload server-side (DataAnnotations / FluentValidation) before persisting.

GPointing the front-end at the API — step by step

  1. Start the .NET API (dotnet run) and note its URL (e.g. https://localhost:7042).
  2. At the root of the front-end, create .env.local (copy of .env.example): 
    VITE_API_BASE_URL=https://localhost:7042/api
  3. Restart the dev server: npm run dev.
  4. The front-end automatically switches to api mode: GET /api/data on startup, PUT /api/data on every change (400 ms debounce).
  5. Check in the Network tab that the calls go to the API. On failure, a red banner shows and the app falls back to the local seed.
Back to localClear VITE_API_BASE_URL (or delete .env.local) and restart.
